### Answered: voice triggers vs the key mapping page

Maintainer asked whether the Voice screen's "Fn hold for speech" / "orange key
opens the assistant" switches could collide with bindings made on the Key
Mapping page. **They cannot.** `KeyMappingScreen.kt` is an inventory, not an
editor: it reads each key's current binding and routes to the screen that owns
it. In `toolbox/KeyInventory.kt`, Sym and the orange side key are both
`Editor.VOICE`, Fn is `Editor.FN_LAYER`, Space is `Editor.TRACKPAD`. The Voice
screen is the single source of truth for those two bindings; Key Mapping only
displays them. No double-binding is possible, and no change is needed.

## THE UPGRADE HAZARD, AND WHAT WE DID ABOUT IT

Found on the maintainer's Titan on 2026-08-28, not by reading the diff.

### The problem

The 2.0 branch changed the Gradle namespace from `it.palsoftware.pastiera` to
`brobata.physiboard`. `AndroidManifest.xml` declares the IME with a *relative*
class name (`.inputmethod.PhysicalKeyboardInputMethodService`), so the resolved
component name moved with the namespace:

    1.2.4  brobata.physiboard/it.palsoftware.pastiera.inputmethod.PhysicalKeyboardInputMethodService
    2.0    brobata.physiboard/brobata.physiboard.inputmethod.PhysicalKeyboardInputMethodService

Android identifies an input method by component name. On upgrade the stored
selection points at a component that no longer exists, so the system falls back
to another keyboard — on the Titan it dropped to `com.iqqijni.bbkeyboard`. The
phone's `enabled_input_methods` was observed carrying both forms at once.

Every existing user would have to re-enable *and* re-select PhysiBoard by hand,
with no explanation. On a phone bought for its physical keyboard that reads as
"the update broke my keyboard".

### The option not taken

Declaring the old component alongside the new one would preserve the selection,
but both would then be real input methods and the keyboard picker would show
**two "PhysiBoard" entries permanently**. Rejected on that basis.

### What was built

`PackageReplacedReceiver` — a manifest receiver for
`ACTION_MY_PACKAGE_REPLACED`, which is exempt from the implicit-broadcast
restrictions and so still reaches a manifest receiver. On an update it compares
the selected IME *component* against this build's own service (comparing
packages alone is not enough — the stale 1.x component shares our package name)
and, only when we are not it, posts a high-importance notification, "Pick
PhysiBoard again", that opens straight into setup.

Verified on the AVD both ways: notification ID 3 posted when another keyboard was
selected, and nothing posted when PhysiBoard was still selected, so upgrades
after 2.0 stay silent.

**Known limitation:** `POST_NOTIFICATIONS` is a runtime grant on Android 13+. If
a user has denied it this does nothing, and the receiver cannot request it. The
in-app setup screen still explains the situation for that case.
